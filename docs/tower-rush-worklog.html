01
Core rules

Arithmetic before any pixels

core/TowerRules.ts · Vitest-style assertions

Read the build plan and adopted its one architectural rule: the game rules import nothing — not the engine, not a service, not a DOM type. resolve() takes numbers and returns numbers. That buys a test suite that runs in milliseconds, difficulty tuning in a plain script, and a port that is one file of arithmetic rather than a rewrite.

Implemented the slice maths: perfect-stack tolerance, overlap as the intersection of two spans, and the offcut geometry for the falling debris. Then turned the plan's edge-case table into executable assertions rather than transcribed prose — ten cases, each checked against three invariants.

Verified
Edge cases passing (containment, width conservation, offcut non-overlap)10 / 10
Float-precision case: tap at 60.30000000001 resolves tox 30.200 · w 139.800
Fairness floor — a miss is ovW <= MIN_WIDTH, not <= 020 px

That last line looks like a boundary condition and is really a feel decision: ending a run on a 20 px sliver reads as fair, ending it on a 0.4 px hairline reads as a bug.

02
Screens

Every screen, then a change of direction

720 × 1280 mockup · art direction revised mid-flight

Built an interactive mockup of the full screen set with the loop playable inside it, so the feel could be judged before committing engine code. One constraint shaped all of them: during play the entire screen is the tap target, so nothing touchable may sit on the play surface — sustained accidental ad clicks are an invalid-traffic problem that suspends ad accounts, not merely bad feel.

Art direction then changed from abstract blocks to Tower Rush, a crane-drop shop stacker, and the mockup was rebuilt against the new reference sheets.

Reviewing those sheets raised a scope question worth recording: they contained hearts, a level-complete panel with stars, a shop-upgrade panel, and a four-item crafting resource set. Each implies a mechanic the plan does not have.

Scope raised by the art

Discrete levels, star goals, map screen+5 d
Per-shop upgrade tree+4 d

Recommendation recorded: ship the endless game with the full art and the sky progression; hold the meta layer for a follow-up built only if retention justifies it. A heart costs an hour of art and a week of refill-timer balancing.

Cutting usable sprites out of the sheets

Sliced the supplied sheets into individual sprites by analysing the alpha channel rather than assuming a fixed grid — the layouts were irregular and a grid would have clipped. Extracted thirteen storefronts, the logo lockup, the parchment sign, the lamp post and three city plates.

04
The game

A responsive build, and the stacking bug

Single-file game · canvas + DOM overlay

Built the playable game around one layout rule: the world is always 720 units wide and its height is whatever the device gives. Every UI size is expressed in world units through a single CSS variable, so a phone, a tablet and a desktop are identically proportioned with no separate breakpoints. Past a 0.62 aspect the stage letterboxes to a portrait column rather than stretching.

The sky changes in chapters as the tower climbs — a settled stretch of one plate, then a short cross-fade into the next — which turns the background into the clearest progress signal in the game.

The significant bug of the day: stacked shops showed a visible gap. The cause was that each sprite includes a roof topper — a coffee cup, a pretzel, a stack of books — so stacking on the full sprite box meant every shop rested on the topper of the one below, with the transparent space either side reading as a gap.

Topper as a share of sprite height
Largest (bank — pediment and coin)33.7 %
Typical19 – 26 %
Smallest (wine store — flat parapet)0.3 %
Adjacent block tops after the fix, exactly one BLOCK_H apart921 → 681

Fixed by splitting each sprite: the body fills the block box exactly, the topper overhangs above it and is covered by the shop stacked on top — which is precisely what the gameplay reference shows. Slicing is a horizontal 3-slice, so the outer thirds hold their scale and a narrowed shop keeps its doorway and planters instead of distorting.

06
Playtest

Five defects from real device testing

Reported on device · each traced to a cause

Testing on hardware produced five reports. Each was diagnosed to a specific cause rather than patched at the symptom:

Defects fixed
Garbled text. No <meta charset>, so the server defaulted to windows-1252 and every multi-byte glyph shattered. Added it and removed all non-ASCII from markup and codemojibake
Blurred buttons. A 168 px bitmap face drawn at 558 device px on a 1080/dpr3 phone; source icons only ≈40 px native, so no re-export helps. Rebuilt the face in CSS and the glyphs as SVG3.3× upscale
Abrupt ending. The missed shop faded to nothing instead of falling, and the camera pulled back on the same frame0.71 s fade
Best score looked frozen. The HUD showed max(best, score), so on a first run it simply mirrored the score. Now shows the standing record, or NEW BESTdisplay only
Skins unreachable from Game Over. All screen layers share one z-index, so DOM order decides, and the Game Over layer sits after Skins — it rendered behind and its dim swallowed the tapsz-index 10

The ending is now staged so the fall is actually watched: the camera holds still for 0.62 s, the shop clears the screen at 1.29 s, and the score panel arrives at 1.75 s. Ordinary slice offcuts keep their gentle fade; only the fatal one is preserved.

One fix introduced a bug of its own, caught by testing the flow rather than the change: re-rendering the skins grid re-entered the open routine and discarded the "return here" target, dropping the player to the menu instead of back to Game Over.

5 defects resolvedRegression caught in test
07
Platform

Reviewing the asset and analytics platform

PanScienceInnovation / Game-Dev · main

Cloned and read through the platform repository. Four components: an Express and PostgreSQL backend, a React admin dashboard, the original Flutter and Flame match-3 client, and a Phaser integration for a game living outside the repo — with Docker Compose, nginx and certbot for deployment.

The recent migrations are the substance of the repo, and they generalise it away from being one match-3 game:

Schema direction
010 — games registry; assets, collections and sessions scoped by gameships empty
011 — interaction types widened past the match-3 vocabulary+4 types
012 — slots, with a partial unique index enforcing one active asset per slot per gamereplaces "newest wins"
Feature branches ahead of main0 of 4

Two things to raise. The README still describes the project as a single Candy Crush platform, which no longer matches the schema. And GET /api/collections returns 500 without an order parameter — order.toLowerCase() is called on an undefined value.

The brick-breaker integration is the clearest artefact in the repo and reads as the template for adding any game: rewrite the sprite table before the loader runs, match by asset name, fail open so a downed backend leaves the built-in art untouched, and never introduce a texture key the game does not already have. Tower Rush is the same shape — a self-contained page inside a Capacitor package — so that path applies directly.
